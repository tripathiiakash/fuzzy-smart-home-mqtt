# Fuzzy Logic Smart Home Automation over MQTT (IoT + Computational Intelligence)

A simulated IoT smart home. Virtual sensors (temperature, humidity, light intensity,
occupancy) publish readings over **MQTT**; a **fuzzy logic controller** subscribes,
decides **fan speed, AC power and light brightness**, and publishes the commands back.

> **Honest scope note (put this in your report's first paragraph):** sensors and
> actuators are *simulated in software*. The architecture - sensor node, MQTT broker,
> controller, actuator, dashboard - is the real IoT pattern. The sensor script can be
> replaced by an ESP32 publishing to the same topics without touching the controller.

## Architecture

```
 sensors.py  --publish-->  MQTT broker  --subscribe-->  controller.py (fuzzy logic)
 (4 virtual                (HiveMQ or                         |
  sensor nodes)             Mosquitto)  <--publish-- actuator commands (fan / ac / light)
                                |
                                +--subscribe--> dashboard.py (live graphs)
```

Topics (under `iot_ci_fuzzy_home_7q2/livingroom/`):
`sensors/temperature|humidity|light|occupancy` and `actuators/fan|ac|light`.
Payload: `{"value": 31.2, "time": "10:15"}`.

```bash
python controller.py                     # terminal 1: start the brain first
python dashboard.py                      # terminal 2: live graphs
python sensors.py --delay 0.2            # terminal 3: a whole day in ~1 minute
```

By default it uses the free public broker `broker.hivemq.com`. Because that broker is
shared with everyone, **change `MQTT_ROOT`** (in `config.py` or as an environment
variable) to something unique to you. To run fully offline, install Mosquitto and set
`MQTT_BROKER=localhost`.

## How the fuzzy controllers work

| Controller | Inputs | Output | Rules |
|---|---|---|---|
| Fan | temperature, humidity, occupancy | 0-100 % | 9 written (15 after OR-expansion) |
| AC | temperature, humidity, occupancy | 0-100 % | 12 written (15 after OR-expansion) |
| Light | light intensity, occupancy | 0-100 % | 5 written (7 after OR-expansion) |

Splitting into three small controllers avoids one 3^4 = 81 rule base.

Pipeline: **fuzzification** (trapezoidal/triangular membership functions) ->
**rule evaluation** (AND = min) -> **implication** (clip output set by firing strength) ->
**aggregation** (max) -> **defuzzification** (centroid). Example rules:

- IF occupancy is empty THEN fan is off
- IF temperature is hot AND someone is in the room THEN fan is high
- IF temperature is warm AND humidity is humid AND room is crowded THEN AC is high
- IF someone is in the room AND light is dark THEN lights are high

## Results (one simulated day, seed 42 - re-run `run_offline.py` for exact numbers)

| | Fuzzy | If-else threshold |
|---|---|---|
| Total energy | 13.69 kWh | 15.73 kWh (fuzzy saves ~13 %) |
| AC ON/OFF switch events | 5 | 18 |
| AC average output jump per 5 min | 4.0 points | 6.3 points |
| Light ON/OFF switch events | 17 | 5 |

Read these honestly - they are part of your analysis:

- **Energy saving assumes appliance power scales with its output level** (like an
  inverter AC). The if-else controller can only run the AC at 100 %, which is where most
  of the saving comes from. Say this in the viva.
- **Fuzzy is smoother and gentler on the AC, but flickers more on the lights**, because
  the simulated occupancy count jitters (people walking in and out). A real design would
  add hysteresis or a short delay - a good "future work" point.
- **The fuzzy AC uses ~2.7 kWh while the room is empty** (the "pre-cool when hot and
  empty" rule). That is a deliberate design choice; remove that rule to save energy at
  the cost of a warmer room on arrival.
- There is no thermal model of the room, so comfort is not measured, only energy and
  switching behaviour.

## Likely viva questions

- **Why fuzzy logic here?** Comfort is not binary: "warm" and "hot" overlap, and fuzzy
  gives graded outputs instead of ON/OFF jumps.
- **Explain fuzzification / defuzzification.** See the pipeline above; centroid =
  centre of gravity of the aggregated output shape.
- **Why three controllers?** Keeps rule bases small (about 5-12 rules instead of 81).
- **What is MQTT?** Lightweight publish/subscribe protocol; a broker routes messages by
  topic; QoS 0/1/2 sets delivery guarantees (this project uses QoS 0).
- **Is it real IoT?** Sensors are simulated, but the publisher -> broker -> subscriber
  -> actuator architecture is the same as a real deployment.
- **Why did you write the fuzzy engine yourself?** To show the five steps explicitly
  rather than hiding them inside a library.
